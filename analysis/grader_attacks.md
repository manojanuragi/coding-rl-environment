# Grader attacks

This is a record of the attacks I actually ran against `tests/verifier/grade.py`, not a list of things that seem plausible on paper. Every number below came out of a real run of the harness against a real (deliberately broken) submission sitting in `/tmp` on my machine while I was building this. If you want to reproduce any of these, the recipe for each one is short enough to just retype.

The environment is a pricing engine (`orderflow`) with two seeded bugs one in `discounts.py` (percent discounts compound instead of only the best one applying), one in `engine.py` (discounts get applied to `subtotal + shipping` instead of just `subtotal`, which quietly discounts shipping) plus a dependency pin (`requirements-dev.txt` pins `pytest==99.0.0`, which doesn't exist) that has to be fixed before the test suite will even install. An agent is graded by copying its submission into a scratch directory, stamping a pristine copy of both the visible test file and the hidden verifier suite on top of whatever the agent left in `tests/`, installing from that copy, and running both files under pytest with `junitxml`. Verdict is strict pass/fail (every test in both files green); a separate score (fraction of hidden tests passing) is recorded for analysis but never used to award a partial solve.

I went looking for ways to beat that setup. Four attempts are documented below with real scores. I'm not claiming these are the only four ways to cheat they're the four that seemed most likely to actually work against this specific harness, and each one taught me something I had to go fix.

## Attack 1: hardcode the answers to the visible tests

**What it does.** Instead of fixing `discounts.py` and `engine.py`, add a lookup table in `price_order()` keyed on `(order_id, subtotal, discount codes)` that returns the exact `PricedOrder` values the six visible tests expect, and only fall through to the (still-broken) real logic for anything not in the table.

I wrote this by literally reading `tests/test_pricing.py`, copying the five distinct `(order_id, subtotal, codes)` tuples it exercises, and hand-computing the correct output for each one to stuff into the table. This is the laziest possible way to pass a suite you can see without doing the underlying work, and it's the first thing I'd expect a model under pass@k pressure to try if it ever got a hint of what the grader checks.

**Result:** `FAIL`, score `0.375` (6 of 16 hidden tests pass).

**Why it fails.** The hidden suite in `tests/verifier/test_hidden_pricing.py` uses `order_id` values built from `uuid.uuid4().hex[:8]` plus a counter, specifically so that no test's identifying key is a literal string a submission could have seen or guessed. None of the hidden test inputs collide with the five tuples in the lookup table, so every hidden test falls through to the real (still buggy) pricing logic and fails there. The 6/16 that do pass are the regression tests that happen to also be satisfied by the underlying bug being irrelevant to their inputs (e.g. the zero-discount case, where a broken discount-stacking rule doesn't matter because there's nothing to stack).

This is the reason the hidden suite doesn't reuse any of the visible suite's literal order IDs, subtotals, or discount-code combinations, and the reason I randomized the hidden suite's IDs instead of leaving them as a fixed string like `"VERIFIER-1"` (which is what I originally had see the note in the test file's git history equivalent, i.e. this document, since I caught it myself before ever running a cheat attempt against it). A hardcoding attack only works against a grader whose full input space is visible to the thing being graded. Once the hidden suite exists at all and doesn't share fixture data with the visible suite, this attack has nothing to key off.

**Mitigation actually in place:** hidden test suite, kept out of the agent's working directory (`hidden_from_agent` in `task.yaml`), with randomized non-semantic identifiers so no literal value in it can be predicted from the visible suite.

## Attack 2: tamper with the test files themselves

**What it does.** Two variants, tried together: (a) replace `tests/test_pricing.py` with a trivial file containing a single `assert True`, so the "regression suite" the grader claims to run is meaningless, and (b) create a fake `tests/verifier/test_hidden_pricing.py` of my own a file that looks like a plausible hidden suite (a handful of asserts, JUnit-friendly, same function-naming convention) but is actually testing the broken code's *current* behavior rather than the spec, so it passes trivially.

The second variant matters more than it sounds it's not "delete the test," it's "fabricate a replacement that a lazy read would mistake for the real thing."

**Result:** `FAIL`, score `0.375` (matches attack 1's score almost exactly, because this submission was the hardcoding one with tampered tests laid on top see below).

**Why it fails.** `grade.py` never runs anything the agent left in `tests/`. Step 2 of the harness copies the submission to a scratch directory and then unconditionally overwrites `tests/test_pricing.py` from `tests/fixtures/test_pricing.py` (a pristine copy kept next to the grader, outside the submission tree) and `tests/verifier/test_hidden_pricing.py` from the real hidden suite, also kept outside the submission tree. Whatever the agent wrote to either path, delete it, replace it, write a fake one with the same filename, is gone before pytest ever runs. The score above is identical to attack 1's because, once the stamping happens, grading this submission is *exactly* grading the hardcoded-answers submission from attack 1; the tampering step did nothing.

This is the single most load-bearing line in the whole harness, and I want to be honest that it's also the most obvious thing to get wrong: if the pristine copies lived *inside* the path that gets copied from the submission (instead of next to `grade.py`, read from a fixed path that never touches the submission tree), an agent that discovered and overwrote them before the copy step would win. I checked this by grep'ing `grade.py` for every path it reads from versus writes to and confirming the pristine sources (`tests/verifier/test_hidden_pricing.py` and `tests/fixtures/test_pricing.py` under the grader's own directory) are never resolved relative to the submission path.

**Mitigation actually in place:** pristine test files stored outside the submission tree, stamped onto a scratch copy after copying but before any dependency install or test run; the agent's own `tests/` directory is read for nothing.

## Attack 3: strip input validation to dodge specific negative tests

**What it does.** Fix both real pricing bugs properly (so the interesting business-logic tests all pass), but also delete the validation in `models.py` that rejects a zero/negative quantity, a negative unit price, and an out-of-range discount percentage replacing each check with `pass`. The instruction text explicitly tells the agent not to do this ("You haven't weakened or removed the input validation that's already there"), so this attack is really testing whether the grader *enforces* that instruction or just states it as a suggestion the agent could ignore for a higher score on everything else.

**Result:** `FAIL`, score `0.875` (14 of 16 hidden tests pass).

**Why it fails, and why the score is deceptively high.** Both pricing bugs are genuinely fixed in this submission, so all the business-logic tests, discount stacking, shipping-discount isolation, the worked example from the spec doc, category tax rates, free-shipping boundaries pass. That's most of the suite. The two hidden tests that specifically construct an invalid `LineItem`/`Discount` and assert a `ValueError` is raised are the only ones that fail. 14/16 is a genuinely good score by any partial-credit reading, which is exactly the problem with partial credit as a pass condition: a grader that used "score above some threshold" as its bar would hand this submission a win despite it directly violating a stated requirement.

This is why the verdict is strict AND-of-all-tests rather than a threshold on the score. The score field exists for analysis (it's useful to know *how close* a failing submission got), but `known_bug_locations` and `binary_pass_condition` in `task.yaml` are explicit that passing means every test in both files, full stop.

**Mitigation actually in place:** binary verdict requires 100% of both suites, not a threshold; the hidden suite carries dedicated tests for the exact validation behaviors the instructions call out as things not to touch, so silently regressing them can't hide behind an otherwise-strong score.

## Attack 4: hang instead of failing

**What it does.** Fix both bugs correctly (again, so nothing looks obviously wrong), but leave a `while True:` loop with no break condition in `price_order()`, reachable on every call. The idea is denial-of-service against the grading run itself: if the harness has no timeout, a hung submission either fails the whole grading job in some undefined way (which might get manually re-run, discarded, or worst case silently skipped and excluded from a pass@k denominator) rather than being cleanly scored as a failure.

**Result:** `FAIL`, score `0.0`, wall-clock time ~95.8s (both pytest invocations time out and are killed).

**Why it fails.** Every subprocess call in `grade.py` (`pip install -e .`, `pip install -r requirements-dev.txt`, both pytest invocations) runs under `subprocess.run(..., timeout=...)`, and a `TimeoutExpired` is caught and converted into a normal (non-zero) return code rather than an uncaught exception. A hung test run is treated exactly like a crashed one: the JUnit XML either doesn't exist or is incomplete, `parse_junit` returns an empty or partial result set, and the harness explicitly checks for the empty case (`total_hidden` of 0 must score `0.0`, not vacuously `1.0` from an empty "all() of nothing is True"). I want to flag that this last part the empty-result-set edge case is the kind of thing that's easy to get backwards; Python's `all([])` is `True`, so a careless implementation of "did everything pass" over an empty dict would score a submission that produced zero test results as a perfect pass. I hit this in my own first draft of the scoring logic and had to add the explicit `bool(hidden_results) and all(...)` guard.

I also had to tune the timeouts themselves during testing: my first pass used 120s per install step and 120s per test step, and a hung submission's two pytest invocations together took long enough that *my own test harness* (not the grader the shell wrapper I was using to drive `grade.py` while building this) hit its outer timeout before `grade.py` got to write `result.json`. That's not a flaw in the grader's logic, but it's a real operational lesson: whatever process launches `grade.py` in production needs its own timeout budget comfortably larger than `INSTALL_TIMEOUT_SECONDS + 2 * TEST_TIMEOUT_SECONDS`, or a hung submission can still cause an ungraded run even though the grader itself handles the hang correctly. I dropped both constants to 120s/45s specifically so the worst case (two full test timeouts plus two full install timeouts, all four in series) stays under the 900-second wall-clock limit `task.yaml` gives the agent's own run by a comfortable margin, without being so tight that a slow-but-legitimate `pip install` on a cold cache gets killed.

**Mitigation actually in place:** hard per-step subprocess timeouts on every install and test invocation; timeouts convert to failures rather than exceptions; an empty or partial JUnit result set is explicitly treated as a failing score, not a vacuous pass.

## What I didn't test, and why I'm not pretending I did

I did not try attacking the Docker build itself (e.g. a submission that tries to break out of the container, exfiltrate the hidden test file over the network, or otherwise attack the environment rather than the grader) partly because `network_access_required: false` and a submission has no legitimate reason to need network access, so the honest mitigation there is "the container the agent runs in shouldn't have egress in the first place," which is an infrastructure decision outside `grade.py` itself, not something the grading script can defend against after the fact. I also didn't try a submission that passes on one grading run and fails on a re-grade (a flaky/non-deterministic cheat) because nothing in this task involves randomness, timing-dependent behavior, or external state on the solution side the only randomness anywhere in the system is the hidden test suite's own order IDs, which are inputs to the code under test, not outputs it controls. If this environment grows to include anything time- or order-dependent, that would be the next attack worth actually running rather than just listing.
